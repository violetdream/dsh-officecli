dsh-officecli Agent 插件 架构设计分析

仓库：github.com/violetdream/dsh-officecli · DeepSeek-Harness (DSH) 插件 · 让 Agent 用自然语言创建/编辑 Office 文档（docx / xlsx / pptx）· TypeScript + React + Node.js · MIT

01核心设计思想：为什么需要这层插件

一句话：OfficeCLI 没有布局引擎，模型直接调 add shape 坐标必歪 —— 插件在「模型意图」与「命令行原语」之间插入一个 PPT 设计编译层。
官方定位："Positioning is explicit — no layout engine, you own the grid math"（坐标是显式的，没有布局引擎，网格数学由调用方负责）。如果让 AI 模型直接下发底层 add shape 并自己填坐标，排版几乎必然摆歪。因此插件形成一个三段式职责链：
图 1 · 三段式职责链：模型只负责内容，设计层负责排版数学，OfficeCLI 只负责执行
docx / xlsx 为什么不进设计层？—— 它们是结构化流式文档，编辑贴近原语即可，无需布局数学；插件对这两类只提供 12 个底层原语工具。真正需要"设计"的只有 pptx，于是沉淀出 3 个高层工具 + 一整套设计系统（15 种版式 / 8 套主题 / 6 套模板）。

02系统全景架构

插件是「双半结构」：宿主半跑在 DSH 的 Node 进程里（cordis 插件机制），客户端半是注入 Web UI 的 React bundle，两者经 HTTP/SSE 协作。
图 2 · 系统全景：浏览器双半 ↔ 插件宿主半（cordis）↔ OfficeCLI ↔ 会话工作区
分层职责（自上而下）
  • 表现层 — React 客户端半：侧边栏入口、预览浮层（PreviewPanel），样式走宿主 --dsw-* 变量保证视觉一致
  • 框架层 — cordis 依赖注入：ctx.tools / ctx.webServer / ctx.attachments，可选服务必须 ctx.inject 延迟获取（踩坑 #1）
  • 设计层 — 纯 TS 的 pptx/ 编译器：DeckSpec → ShapeOp → officecli 命令，无任何 IO 副作用，可独立测试
  • 工具层 — 15 个 AI 工具注册进 Agent 工具表，含公共校验（common.ts）
  • 基础设施层 — service / workspace / watch / proxy / events：进程管理、隔离、代理、推送
  • 外部命令 — OfficeCLI exe：唯一落盘执行者，watch 子命令额外提供预览服务

03工具体系：12 底层原语 + 3 高层设计工具

12 个底层原语（docx / xlsx / pptx 通用）
office_createoffice_listoffice_viewoffice_getoffice_queryoffice_setoffice_addoffice_removeoffice_moveoffice_batch（原子事务·失败回滚）office_dumpoffice_screenshot
模型用它们对文档做贴近 OOXML 原语的精确读写。office_batch 先在临时副本上全部执行成功才 Replace，失败可定位到具体命令——原子性靠"副本先行"而非事务日志。
3 个高层 PPT 工具（推荐调用顺序）
1
office_design_guide — 返回设计规范/字数红线的结构化分段（guideSections 按 key 组织，防切全文切碎契约）
2
office_deck_create — 模型提交 DeckSpec JSON 一步生成整份 pptx
3
office_screenshot — 渲染 PNG 回传对话，模型"看见"产出后自修正（探测模型 image 模态，不支持则降级结构化校验）
+
office_slide_add — 追加页自动 inferTheme() 还原原文件配色，防突然换肤

04PPT 设计层内部结构（核心资产）

纯 TypeScript 编译器：输入 DeckSpec，输出 officecli 命令序列。设计系统 = 网格 + 主题 + 版式 + 模板 + 红线五个正交概念。
图 3 · DeckSpec 编译管线：红线校验 → 主题/版式解析 → 网格数学 → ShapeOp → batch 命令
设计系统的五个正交概念
① 网格
960×540pt 画布、页边距 32pt、12 栏（栏宽60+槽16）、8pt 基线、母版 A/B/C 三区（标题/内容/页脚）
② 字号阶梯
封面主标题 54pt · KPI 数字 64pt · 页面标题 28pt · 正文 16pt；文本高度 ceil(lines×size×1.35×ls+6+margin×2)
③ 主题 ×8
business-blue（默认）/ academic-crimson / tech-cyan（深）/ warm-orange / gov-red / minimal-gray / nature-green / luxury-black（深），每套 10 色令牌+字体
④ 版式 ×15
cover · section · bullets · cards · kpi · steps · compare · timeline · quote · table · agenda · swot · pricing · roadmap · ending
⑤ 模板 ×6
consulting / product-launch / academic-defense / minimal / gov-report / annual-report —— 与版式正交，一键套"外衣"
+ 字数红线
逐字段上限随设计指南下发：cover.title ≤18字、bullets 标题 ≤22字、kpi.value ≤6字符 —— 在源头抑制溢出而非事后裁剪

06双半结构与构建体系

宿主半 lib/*.js（tsc 编译）
  • tsconfig.json：ES2022 + NodeNext
  • 运行时加载 lib/ 编译产物而非 src/ —— 改完源码必须 pnpm build + 重启 DSH（HMR 默认关闭）
  • 通过 cordis apply() 组装：注入路由、注册工具、启动 watch/proxy
客户端半 lib/client.js（tsdown 打包）
  • client.build.mjs 复刻 closure-factory 协议（banner/intro/footer）
  • 外部白名单 require（react / cordis 等）；config: false 是硬性要求，否则 react 被内联导致 "Invalid hook call"
  • package.json 的 exports 必须含 "./package.json"，否则客户端不进启动图（否则 client.js 404）
  • dsh.client 声明 inject，注册 sidebar.footer.action 插槽
挂载三步（缺一不可）
1
plugin --profile web add <插件目录> — 安装插件包
2
编辑 cordis.patch.yml 插入 id: dsh-officecli 及 config（officecliPath / workspaceDir / watchPort / commandTimeoutMs=30000 / batchTimeoutMs=60000）
3
pnpm dsh web 启动；验证：curl /api/officecli/files?session=probe，路由判定看 Content-Type（json=在册 / text/plain=落 SPA fallback 未注册）

07关键设计决策与踩坑（10 条）

① 可选服务必须 ctx.inject
不能在 apply() 里同步 get('webServer')，否则路由永不注册 —— 依赖注入的时序纪律
② roundRect 的 guide 名是 adj 不是 adj1
写错导致 PowerPoint 判定文件损坏（HRESULT 0x80070570），且 officecli 自查不出
③ 长度必须带单位、不用 zorder
裸数字被当 EMU；zorder 值越大越靠后，背景改用插入顺序置底
④ HTML 改写"一条规则 + g 标志"
否则 POST /api/selection 打到 DSH 自身 404，修复后正确代理到上游 204
⑤ 中文文件名黑名单正则
放弃白名单，改 /^[^\\/:*?"<>|\r\n]+\.(docx|xlsx|pptx)$/i，放行 CJK/emoji
⑥ workspaceDir 必须绝对路径
相对路径导致 <sid>/<sid>/ 重复层级
⑦ 模型看不到图不能假装看过
screenshot 探测 image 模态，未声明则降级结构化校验
⑧ 追加页必须继承原配色
inferTheme() 从 format 属性还原主题，防追加页突然换肤
⑨ 设计指南结构化分段
guideSections() 按 key 组织，防上下文切分把契约切碎
⑩ batch 是原子事务
临时副本全成功才 Replace，失败可定位具体命令 —— 副本先行而非日志回放

09设计思路总结

核心抽象
设计编译层：把"模型不会排版数学"这个问题从提示工程层面（求模型算准坐标）转为架构层面（模型声明意图，代码算坐标）。DeckSpec 是模型与排版细节之间的契约边界。
质量闭环
字数红线（前置抑制）+ 截图自检（事后验证）双保险：红线在生成前约束输入，截图在生成后让模型视觉校验 —— 唯一依赖是模型需声明 image 模态，不支持则诚实降级。
工程纪律
安全（spawn 数组/会话隔离/文件名防逃逸）、原子性（batch 副本先行）、诚实性（能力探测降级而非假装成功）、原子替换 —— 每条踩坑都沉淀为可复用约束而非一次性补丁。
已知限制：视觉自检依赖模型 image 模态（glm-4.5-air / glm-4.7 未声明，需配 glm-4.6v 等）；native 渲染依赖本机 PowerPoint COM；docx/xlsx 无设计层（模型自组织结构）；watch 有空闲超时与进程残留可能；HMR 默认关闭（改源码必须重新 build）。
